# Retrieval Service

A retriever-agnostic Retrieval-Augmented Generation (RAG) / CRAG evaluation component.

## Current scope

This service currently implements the **retrieval evaluation and retry loop** of a CRAG pipeline.

The flow is:

```text
Query
  ↓
Retriever
  ↓
Retrieved chunks
  ↓
CRAG evaluator
  ├── sufficient → return sufficient context
  │
  └── insufficient → retrieve again → evaluate again
```

The current retriever is a `FakeRetriever` used only for development and testing because the real vector database, embeddings, and retriever are being developed separately.

### Important

The current second retrieval is **simulated**. The fake retriever returns insufficient chunks on its first call and sufficient chunks on the next call. Intelligent corrective retrieval has not been implemented yet.

Answer generation is also **not part of the current service**. The CRAG evaluator only decides whether the retrieved context is sufficient; a separate generator can use the validated chunks later.

## Components

### `crag/models.py`

Defines the data models used by the service:

- `Chunk` — a retrieved text chunk with an ID, content, and optional metadata.
- `RetrievalDecision` — either `sufficient` or `insufficient`.
- `EvaluationResult` — the evaluator's decision and explanation.

### `crag/prompts.py`

Contains the LLM prompt used to evaluate whether retrieved context is sufficient to answer a query.

The evaluator is explicitly instructed **not to answer the user's question**.

### `crag/evaluator.py`

Sends the query and retrieved chunks to the LLM and returns a structured `EvaluationResult`.

It uses:

- Groq for the LLM call
- Instructor for structured Pydantic output
- Pydantic for validation
- `python-dotenv` for loading the API key

### `crag/service.py`

Orchestrates the CRAG loop:

1. Retrieve chunks.
2. Evaluate the chunks.
3. If sufficient, stop and return them.
4. If insufficient, try retrieval again up to `max_attempts`.
5. If all attempts are insufficient, return the last result.

The retriever is injected into the service, so the service does not depend on a particular vector database or retrieval implementation.

### `fake_retriever/fake_retriever.py`

Temporary retriever used for development.

It simulates:

- first retrieval → insufficient chunks
- second retrieval → sufficient chunks

It will eventually be replaced or bypassed when the real retriever is available.

### `tests/`

Contains:

- `test_evaluator.py` — manually tests the LLM evaluator.
- `test_crag.py` — tests the complete CRAG retrieval/evaluation flow.
- `test_cases.json` — synthetic sufficient/insufficient evaluation examples.
- `evaluate_dataset.py` — runs the evaluator over the synthetic dataset and reports accuracy.

## Setup

Python 3.13 is currently being used for development.

Install the dependencies:

```powershell
python -m pip install -r requirements.txt
```

Create a `.env` file in this directory:

```text
GROQ_API_KEY=your_groq_api_key
```

Do not commit `.env` or share the API key.

The repository-level `.gitignore` should exclude `.env`, `__pycache__/`, and `*.pyc`.

## Running the tests

Run commands from the `retrieval-service` directory.

Use Python module execution rather than executing the test files directly. This keeps imports such as `from crag...` working correctly.

### Evaluator test

```powershell
python -m tests.test_evaluator
```

### End-to-end CRAG test

```powershell
python -m tests.test_crag
```

Expected high-level flow:

```text
Retrieval attempt 1
  → insufficient

Retrieval attempt 2
  → sufficient
```

### Synthetic evaluation dataset

```powershell
python -m tests.evaluate_dataset
```

This reports how many test cases the evaluator classified correctly.

## Component contract

The evaluator accepts:

```python
query: str
chunks: list[Chunk]
```

and returns:

```python
EvaluationResult
```

Conceptually:

```text
query + retrieved chunks
          ↓
      CRAGEvaluator
          ↓
EvaluationResult
    ├── decision
    └── reason
```

The retriever is expected to expose:

```python
retrieve(query: str) -> list[Chunk]
```

This allows the fake retriever to be replaced later with the project's real retrieval implementation.

## Current limitations / next steps

1. Replace `FakeRetriever` with the real retriever.
2. Define the actual corrective retrieval strategy.
3. Decide how the CRAG component should connect to query optimization.
4. Add stronger automated tests and evaluation cases.
5. Decide whether answer generation belongs inside this service or in a separate component.
6. Add an API endpoint if the team decides the service should be independently callable over HTTP.

## Design goal

The main design goal is to keep CRAG independent of:

- the vector database
- the embedding model
- the specific retriever implementation
- the query optimization implementation
- the final answer generator

The service should communicate with other components through clear input/output contracts.
